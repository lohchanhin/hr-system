# 打卡來源：線上打卡與指紋匯入互補

客戶 2026/10/23 的要求（R6）：「線上打卡和指紋記錄，不要互相覆蓋，要互補」。

系統裡的打卡有兩個來源：員工在「出勤打卡」頁面的**線上打卡**，以及管理者在「出勤管理 → 考勤資料匯入」上傳的**考勤機（指紋）檔案**。
兩邊的記錄一律並存、互不覆蓋，所有計算都把它們當成同一組打卡：**每一班的簽到取最早的一筆、簽退取最晚的一筆**。

## 資料欄位

`AttendanceRecord.source`（`server/src/models/AttendanceRecord.js`）：

| 值 | 畫面顯示 | 寫入的地方 |
| --- | --- | --- |
| `online` | 線上 | `POST /api/attendance`（線上打卡，伺服器時間） |
| `import` | 指紋匯入 | `POST /api/attendance/import`（考勤機檔案匯入） |
| `manual` | 手動補登 | 保留給日後的補登功能，目前沒有程式寫入 |
| 沒有欄位（`legacy`） | 未標示 | 這次調整以前的舊資料（線上或匯入都有可能），不回填 |

- 欄位沒有預設值，舊資料維持原樣，部署時不需要資料遷移；讀取時沒有來源一律視為 `legacy`，照常參與計算。
- 新增索引 `attendance_employee_timestamp`（`{ employee: 1, timestamp: 1 }`，非唯一），由 Mongoose 啟動時自動建立（已存在則略過）；匯入比對重複、工時與報表的查詢都用得到。舊資料即使有重複打卡也不影響建立。

## 匯入：只新增、重複略過

`server/src/controllers/attendanceImportController.js`

- 匯入**只會新增**記錄（標示 `source: 'import'`），不會修改或刪除任何既有打卡（線上打卡、先前匯入的、舊資料都一樣）。
- **重複略過**：同一位員工、同一個動作（簽到／簽退…）、時間落在同一分鐘的打卡視為同一筆：
  - 資料庫已經有（不論來源）→ 略過；
  - 同一個檔案裡前面已經出現過 → 略過。
  - 所以同一個檔案再匯入一次，不會多出任何記錄。
- 比對以每 500 筆為一批查一次資料庫（只查這一批的員工與時間範圍）。預覽（`dryRun`）也會比對，管理者在匯入前就看得到會略過幾筆。
- 回應的 `summary` 多了 `duplicateCount`（重複略過的筆數）。`readyCount` 仍是「已對應到員工」的筆數（含重複略過的），`importedCount` 是實際新增的筆數。
- 預覽表格中被略過的列狀態為 `duplicate`（畫面顯示「重複略過」），`duplicateReason` 說明是資料庫已有還是檔案內重複。
- 訊息：
  - 有新增也有略過：`考勤資料匯入完成（新增 X 筆，重複略過 Y 筆）`
  - 全部都是已有的打卡（例如重複匯入）：HTTP 200，`沒有新的打卡記錄：Y 筆與既有打卡記錄重複，已略過`（不是錯誤，畫面以提醒顯示並保留對話框）
  - 同時還有缺少對應員工或驗證錯誤時，重複略過會一併列在 `failureReasons`。
- 比對既有打卡時資料庫出錯：HTTP 500「考勤資料寫入失敗，請稍後再試」。
- 限制：兩位管理者「同時」匯入同一個檔案時，兩邊各自比對時都還沒有對方的資料，可能各新增一次；依序匯入不會重複。

## 線上打卡

`server/src/controllers/attendanceController.js`

- 線上打卡一律標示 `source: 'online'`，時間以伺服器時間為準（不變）。
- 同一班重複的線上簽到／簽退仍然擋下（409）；**指紋匯入的打卡不擋線上打卡**，兩邊都保留，計算時互補。沒有來源的舊資料視同線上打卡，照舊會擋。
- 線上簽退前要有這一班的簽到：線上或指紋匯入的簽到都算（不變）。
  注意：指紋簽到要等管理者匯入後系統才看得到；在匯入之前用線上簽退，仍會因為「沒有簽到」被擋下（維持原本的規則）。
- 打卡算哪一班：讀昨天、今天、**明天**的班表，先照原本的方式選（現在在上班時間內的班 → 今天的班 → 昨天的跨日班），
  選到的班現在不能做這個動作時，改用打卡時段包含現在的那一班（好幾班都包含時取時間最接近的：簽到比上班時間、簽退比下班時間）。
  - 00:00 開始的大夜班，前一晚 23:00（簽到緩衝提早 60 分鐘）起就能簽到，記在明天的大夜班上。
    原本只讀今天與昨天的班表，23:50 簽到會回 400「今日未設定班表，請洽管理員」，或被當成今天已經下班的日班而回「時段已結束」。
  - 今天排休、明天大夜：23:00 以後的簽到照樣可以打（記在明天的班）；其他時間、其他動作仍以「今日為休息日」回覆。
  - 昨天夜班（20:00-08:00）接今天日班：07:55 的簽到算今天的日班、08:05 的簽退算昨天的夜班（原本兩個都會被擋）。
  - 明天的班只在現在已經落在它的打卡時段內時才看；其他情況（包含錯誤訊息）與原本相同。

## 計算：簽到取最早、簽退取最晚

共用的比對在 `server/src/services/attendancePunchService.js` 的 `matchShiftPunches`：

- 以班別時間（考勤時區，預設台灣時間 `ATTENDANCE_TIMEZONE=Asia/Taipei`）加上「打卡緩衝」設定算出這一班的簽到時段、簽退時段（與線上打卡的開放時段、薪資遲到早退判斷相同）。
- 簽到取簽到時段內最早的一筆，簽退取簽退時段內、晚於簽到的最晚一筆，不分來源。
- 例：08:10 線上簽到，之後匯入 07:55 簽到、17:05 簽退 → 這一班以 07:55-17:05 計算，不算遲到；之後再用線上在 17:20 簽退 → 簽退改取 17:20。

### 同一筆打卡只算給一個班

工時、出勤天數與部門報表的出勤、工時，用同一個檔案的 `matchSchedulesPunches`，把一位員工整個月的班表一起比對：

1. 先依每一班的簽到、簽退時段比對（如上）。落在某一班時段內的打卡就保留給那一班；同一筆打卡落在兩個班的時段內時
   （打卡緩衝設得很大才會發生），算給時間比較接近的那一班（簽到比上班時間、簽退比下班時間）。
2. 時段內找不到簽到或簽退的班，才沿用原本依日期比對的方式（遲到超過簽到緩衝、提早超過簽退緩衝的人仍算得到工時），但：
   - 已經被任何一班用掉的打卡不再使用（依日期比對用到的也保留給那一班）；
   - 簽到要早於這一班的下班時間；
   - 簽退要晚於上班時間與簽到，且不晚於下一個班表的開始時間（休息日等不用上班的班表以當天 00:00 為界，有填時間的以開始時間為界）；
     後面沒有班表時（例如月底最後一班，下個月的班表不在這次計算裡），當作隔天休息：不晚於隔天 00:00；
     跨日班（例如夜班 20:00-08:00）不晚於下班時間加簽退緩衝（預設 2 小時）。之後日期的班表最早也是隔天 00:00 才開始，不會拿到它的簽退。

修正的問題（2026-11 複查時在真的資料庫重現）：大夜 00:00-08:00、日薪 2000，10/12 缺勤、10/13 上班
（10/12 23:55 指紋簽到、10/13 08:04 線上簽退）。原本 10/12 依日期比對拿到 23:55 的簽到與隔天的簽退，
10/12、10/13 都算 8.15 小時，`/api/payroll/complete-data` 回 `workDays: 2`、`baseSalary: 4000`；修正後是 1 天、2000。
日班（缺勤那天拿到隔天 07:55 的簽到）、小夜缺勤接大夜、夜班 20:00-08:00 中間缺勤、只打簽到忘了簽退（原本會拿隔天的簽退，算成 30 幾個小時）也都是同一個問題。

對既有資料的影響：部署後重新計算時，缺勤那天不再被算成出勤（日薪、時薪人員的薪資、出勤天數、部門報表的出勤與工時會變少，變成正確的數字）；
有出勤的那天不受影響（下班超過簽退緩衝才用指紋簽退的加班，月中、月底最後一班都照樣算）。比較少見的情況：
月底最後一班是跨日班、又在下班超過簽退緩衝之後才簽退（而且簽退時段內沒有任何簽退），那天不再算出勤；需要時調大「打卡緩衝」的簽退延後時間。

### 對既有資料的影響

- 舊資料不改；部署後重新計算時，同一班同時有多筆打卡的，簽退改取最晚的一筆（原本工時取「簽到後的第一筆簽退」）。
- 部門報表的遲到、早退原本用 UTC 時間比較班別時間，台灣時間的打卡會比錯（幾乎不會出現遲到）；改為與薪資扣款相同的比對後，報表會開始列出實際的遲到、早退。

### 2026-11 第二次複查的修正

- **依日期比對的「當天」**：除了原本的 UTC 日期（台灣 08:00 到隔天 08:00），也包含班表日期的台灣日期當天 00:00 起。
  台灣 08:00 以前的簽到 UTC 日期是前一天：日班 08:00 的人比簽到緩衝更早到（06:50 的指紋簽到；簽到緩衝設成提早 15 分鐘時 07:40 到也一樣），
  以前找不到簽到，整天算成缺勤（日薪少一天）。前一天深夜的簽到仍然不會被當成今天的簽到。
- **跨日班隔天排休**：夜班 20:00-08:00 的隔天排休時，休息日的界線（隔天 00:00）落在班內，提早下班（03:30，不在簽退時段內）的簽退找不到，
  整班算成缺勤；隔天沒有班表或排了上班時卻算得到。現在界線改成下班時間加簽退緩衝（與後面沒有班表時相同），但不超過再下一個上班班表的開始時間。
- **打卡記錄 API**（`GET /api/attendance`）：
  - 每一筆附的員工只有姓名、代號、部門、小單位。以前整份員工資料（薪資、帳號…）跟著每一筆回傳，主管查部門的打卡時看得到同事的薪資。
  - `scope=self`：只要登入者自己的記錄（任何角色）。個人的「出勤打卡」頁要帶這個參數：主管不帶條件時拿到的是部門同仁與直屬部屬的記錄（不含自己），管理員是所有人的記錄。
  - `date=YYYY-MM-DD｜today`、`start`／`end`：以考勤時區（台灣）的日期篩選，`today` 是伺服器現在的台灣日期；格式不對回 400。
  - `limit`：預設最多 1000 筆、上限 5000 筆（由新到舊）。以前管理員不帶條件會把整個資料庫的打卡一次回傳。
  - 員工編號不是有效的 `_id` 回 400（以前 500）。
- **線上打卡的訊息改成中文**：重複打卡「這一班已經完成上班簽到／下班簽退，不需要重複打卡」、沒有簽到就簽退「這一班還沒有上班簽到的記錄，請先完成上班簽到再簽退」（以前是英文）。
- 測試：`server/tests/attendancePunchAssignment.test.js`（最後五項）、`server/tests/attendance.test.js`、`server/tests/timeAudit.integration.test.js`（真的 MongoDB，預設略過）。

### 2026-11 第三次複查的修正：月初第一班

依日期比對時，跨日班找不到當天的簽到會「再看前一天最晚的簽到」。月中前一天的班有自己的打卡（已經被那一班用掉），
但**月初第一天**的前一天是上個月的班，不在這次計算裡，那一班的打卡看起來沒有人用：
11/1 大夜（00:00-08:00，勾了跨日）缺勤，卻用 10/31 小夜的 15:50 簽到、00:05 簽退算成出勤 8.25 小時（日薪多一天，10 月已經領過一次），
部門報表的出勤也算「有簽到」。修正：

- 計算時多讀**月初前一天的班表**，只用來讓那一班認領自己的打卡（`matchSchedulesPunches` 的 `contextOnly`，不在結果裡、不算進這個月）。
  單人計算多查一次；整批計算（薪資總覽、匯出、部門報表）把班表的查詢範圍往前後各多讀幾天，查詢次數不變。
- 「再看前一天的簽到」不用**已經有簽退收尾**的簽到：前一天的簽到之後、這一班上班之前已經有簽退（例如休息日來加班 09:00-18:00），
  那是另一次出勤，不是這一班提早到。月中、月初都一樣。
- 真的提早到的人不受影響：11/1 大夜的人 10/31 22:40 簽到（比簽到緩衝早）、11/1 08:03 簽退，照樣算 11/1 出勤。
- 測試：`server/tests/attendancePunchAssignment.test.js`（最後四項）。
