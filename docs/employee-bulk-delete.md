# 員工批量刪除

後台「人資管理 → 員工管理」可以勾選多位員工一次刪除。**這是永久刪除**，無法復原。

## 使用方式

1. 在員工列表最左邊的勾選欄勾選要刪除的人。表頭的勾選框是「選取本頁」。
   - 管理員的勾選框是灰的，不能選。
   - 換頁時勾選會保留（可以跨頁選）。
   - 搜尋、篩選部門、儲存／刪除／匯入員工之後，勾選會自動清掉（避免刪到看不見的人）。
2. 按工具列的紅色「批量刪除（已選 N 位）」。
3. 確認視窗會列出前 5 位「姓名（員工編號）」與總人數。超過 10 位必須再輸入「刪除」二字才能送出。
   視窗下方的【簽核影響】會列出刪除之後簽核會怎麼樣（見下一節）；這只是提醒，**不會阻擋刪除**，由管理員決定。
4. 完成後會顯示刪除人數、被略過的人與原因，以及有幾位員工因直屬主管被刪而失去主管；
   刪除前盤點到的簽核影響會再提醒一次。

單筆刪除（列表右側的「刪除」）現在也會先跳出同樣的確認視窗與簽核影響，按「確認刪除」才會送出。

## 刪除前的簽核影響

刪除員工不會連動處理簽核資料，所以刪除前會先盤點下列四種情況（只計算「會真的被刪除」的人，管理員與操作者本人不算）：

| 項目 | 意思 |
| --- | --- |
| `pendingRequests` | 進行中的簽核單，正在等這些員工簽核（同一張單只算一次）。刪除後這些單會失去簽核人而卡住 |
| `pendingApprovers` | 上一項依員工拆開：`[{ _id, name, employeeNo, requests }]`，筆數多的在前 |
| `subordinates` | 直屬主管是這些員工、而且本身不在刪除名單內的人數。刪除後他們沒有直屬主管，送出需要主管簽核的申請會被擋下 |
| `workflowSteps` | 簽核流程裡直接指定這些員工（「指定人員」或「指定主管」）的關卡數。刪除後該關卡找不到簽核人 |
| `lostTags` | 這些員工持有、刪除後再也沒有「可簽核」持有者的標籤，而且有流程關卡在使用：`[{ name, requiredByWorkflows }]`。只算帳號啟用且不是離職／留職停薪的持有者 |

另外 `messages` 是給確認視窗直接顯示的中文說明，`incomplete: true` 代表有一段查詢失敗、數字可能偏少（刪除仍會照常進行）。

預覽（不會刪除或修改任何資料）：

`POST /api/employees/delete-impact`（僅管理員），body 同 `bulk-delete`：`{ "ids": ["<員工 _id>", "..."] }`，回應 `{ "requested": 3, "impact": { ... } }`。
單筆與批量刪除的回應也都帶有同一份 `impact`（刪除前盤點的結果）。預覽失敗時前端仍會顯示確認視窗，不會因此無法刪除。

## API

`POST /api/employees/bulk-delete`（僅管理員）

```json
{ "ids": ["<員工 _id>", "..."] }
```

- 一次最多 200 筆，重複的 id 會自動去除；必須是 24 位十六進位字串，物件（例如 `{"$ne":null}`）一律拒絕。
- 回應：

```json
{
  "requested": 3,
  "deletedCount": 2,
  "deleted": [{ "_id": "...", "name": "...", "employeeNo": "..." }],
  "skipped": [{ "_id": "...", "name": "...", "employeeNo": "...", "reason": "admin|self|not_found|changed", "message": "..." }],
  "unassignedSubordinates": 4,
  "impact": { "pendingRequests": 0, "pendingApprovers": [], "subordinates": 0, "workflowSteps": 0, "lostTags": [], "incomplete": false, "messages": [] },
  "warnings": []
}
```

| `reason` | 意思 |
| --- | --- |
| `admin` | 管理員帳戶不可刪除 |
| `self` | 不能刪除自己的帳號 |
| `not_found` | 找不到該員工（可能已被刪除） |
| `changed` | 刪除後仍然存在（例如角色在中途被改成管理員） |

- 單筆刪除（`DELETE /api/employees/:id`）回 `{ "success": true, "unassignedSubordinates": 4, "impact": { ... }, "warnings": [] }`，
  與批量刪除一樣會清掉別人指向這位員工的「直屬主管」；善後失敗只會在 `warnings` 說明，不會讓請求失敗。
- 驗證錯誤回 400；非預期錯誤回 500（不回傳資料庫的內部訊息）。
- 資料庫是單機模式（沒有交易），所以「刪除」之後的任何步驟失敗都不會讓整個請求失敗：已刪除的資料以 200 回報，並在 `warnings` 說明哪一步沒做完。
- 善後是可重試的：重新送出同一批 id（此時會是 `not_found`）也會再清一次「直屬主管指向已不存在的人」。
- 伺服器日誌會留下一行 `Bulk delete employees`，內容只有操作者、人數與被刪除的 `_id`（不含個資），用來事後追查。

## 刪除時會做的事

- 刪除員工帳號資料。
- 清掉其他員工的「直屬主管」欄位（如果指向被刪的人；單筆刪除與批量刪除都會做）。
- 清除員工照片檔案（若沒有其他員工引用）。

## 不會做的事（已知影響，與單筆刪除相同）

員工被刪除後，下列資料**不會**一起刪除，也不會自動處理：

- **考勤、薪資、排班、投保、簽核紀錄會保留**，但上面只剩一個已不存在的員工 id，沒有姓名或編號可以辨識。
  部門報表、薪資總覽等以「現有員工」為基礎的畫面，過去月份的這些人會憑空消失。
- **簽核流程**（刪除前的確認視窗會先提醒，見「刪除前的簽核影響」）：
  - 預設的第 1 關是「直屬主管」。員工的主管被刪除、主管欄位被清除後，這些員工在重新指定主管之前無法送出需要主管簽核的申請。
  - 某個簽核標籤（例如「人資」「排班負責人」）如果所有持有者都被刪除，需要該標籤的表單會變成無法送出。
  - 正在等待某位已刪除的簽核人處理的申請，會失去簽核人而卡住。處理方式有兩種，都由管理員在該申請單的明細操作：
    1. **管理員代為處理**：用「代為核可／否決／退簽」處理卡住的那一關（管理員不是這一關的簽核人，所以是代為處理）。
       單據上會留下一筆「管理員代為…」的紀錄；代為核可時，這一關其他還沒簽的人一律記為免簽。
    2. **退簽後重新送出**：管理員代為「退簽」，單據退回上一個有簽核人的關卡，沒有的話退回申請人；申請人修改後按「重新送出」，
       系統會重新解析每一關的簽核人（已刪除的人不會再被派到），並從第一個有簽核人的關卡重新簽核。
    刪除員工本身不會自動轉派這些單，所以刪除前請先看確認視窗裡的【簽核影響】。
  - 流程關卡直接指定了已刪除的員工，該關卡會找不到簽核人，需要到流程設定改派。
- 部門設定裡的「部門主管」若是被刪的員工，會變成無效值（畫面上顯示為一串 id）。

因此：**離職員工建議把狀態改成「離職員工」，不要刪除**，歷史資料與報表才會完整。批量刪除適合用在測試帳號、誤匯入的資料。
刪除有簽核標籤、當直屬主管或正在簽核中的員工之前，請先看確認視窗裡的【簽核影響】。

## 已一併修正的相關問題

薪資的銀行匯款匯出（臺企、台中銀）以前遇到「員工已被刪除」的薪資記錄會整份當掉，現在會略過那幾筆並在日誌留下警告。
