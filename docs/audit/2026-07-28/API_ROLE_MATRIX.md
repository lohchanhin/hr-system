# API 與角色權限矩陣

稽核日期：2026-07-28
角色：`employee`、`supervisor`、`admin`
原則：先驗證角色，再驗證組織、部門、本人或負責範圍；無權存取時回傳一致的 `401/403/404`，不得藉錯誤訊息洩漏物件存在性。

## 權限矩陣

表中「目前」來自程式閱讀及隔離 MongoDB 動態測試；未列出的路由仍應採預設拒絕。

| 介面或資源 | 員工應有權限 | 主管應有權限 | 管理員應有權限 | 目前觀察 | 風險 |
| --- | --- | --- | --- | --- | --- |
| 登入、登出、本人資料 | 登入、登出、讀取本人必要欄位 | 同員工 | 同員工，另可管理帳號 | 登入無速率限制；JWT 角色不會隨權限變更即時失效 | P2 |
| `GET /api/employees` | 不可列出全公司敏感資料 | 僅負責範圍，且欄位最小化 | 依職務需求分頁查詢 | 員工可列出全部，回傳身分、醫療、薪資與銀行等欄位 | P1 |
| `GET /api/employees/:id` | 僅本人公開或必要欄位 | 本人及負責範圍 | 依職務需求 | 員工可用任意 ID 讀取他人完整資料 | P1 |
| 員工特休餘額 | 僅本人 | 本人及直屬範圍 | 可管理但須稽核 | 多處以路由 ID 或請求欄位決定對象，授權不一致 | P1 |
| 打卡與出勤查詢 | 寫入本人、查詢本人 | 查詢直屬範圍；人工修正需獨立權限與理由 | 管理範圍，完整稽核 | 員工可提交管理員 ID 的外出打卡並成功保存 | P0 |
| `GET /api/schedules` | 僅本人必要班表 | 負責部門或人員 | 組織範圍 | 員工可讀取全部班表，且 `populate` 完整員工資料 | P1 |
| 班表月份、單筆、匯出 | 本人 | 負責範圍 | 組織範圍 | 多個入口缺少物件層範圍驗證 | P1 |
| 班表建立、修改、刪除 | 無 | 僅負責範圍，重要變更需稽核 | 組織範圍 | 主管可刪除不屬於自己的班表；刪除路由缺主管驗證 | P0 |
| 建立簽核單 | 僅以本人為申請人 | 本人；代辦需明確代理權 | 可代辦但須記錄原始與代理人 | 請求可提供 `applicant_employee_id`，缺少可靠綁定 | P1 |
| 簽核單列表、收件匣、歷史 | 本人相關 | 實際待簽及負責範圍 | 稽核或管理範圍 | 查詢參數 `employee_id` 可代查他人資料 | P1 |
| `GET /api/approvals/:id` | 僅本人相關 | 僅待簽或負責範圍 | 管理範圍 | 任意 ID 讀取的物件授權不足 | P1 |
| 核准、駁回、退回 | 無，除非為該節點合法簽核人 | 僅本人當前待簽節點 | 管理例外需獨立權限與稽核 | Controller 信任 body `employee_id`；員工可冒充主管完成核准 | P0 |
| 薪資與銀行資料 | 僅本人必要期間與欄位 | 原則不可見，除非另授權 | 薪資角色，不應等同所有 admin | 可透過員工完整資料介面外洩；缺少專屬薪資角色 | P1 |
| 保險與勞退設定 | 僅本人結果摘要 | 依職務可查結果，不可任意改公式 | 專責角色版本化維護 | 多個設定路由直接接受 body 欄位，存在 mass assignment | P2 |
| 報表 | 僅本人報表 | 負責範圍彙總 | 依資料域授權 | 查詢範圍與底層 API 授權不一致 | P1/P2 |
| `/upload/*` 附件與照片 | 僅本人或該流程合法參與者 | 僅負責流程 | 依資料域授權 | 靜態公開，不需 JWT；可猜址讀取個資附件 | P1 |

| 測試 | 期望 | 實際結果 | 判定 |
| --- | --- | --- | --- |
| 未登入列出員工 | `401` | `401` | 通過 |
| 員工列出全部員工 | `403` 或本人最小資料 | `200`，取得三筆且含管理員敏感欄位 | 失敗，P1 |
| 員工以 ID 讀取管理員 | `403/404` | `200`，含身分證號與薪資資料 | 失敗，P1 |

| 主管刪除非所屬班表 | `403/404` | `200` 且班表消失 | 失敗，P0 |
| 員工列出全部班表 | 僅本人班表 | `200`，可讀全部資料 | 失敗，P1 |

## 必要授權規則

1. 身分一律由驗證後的 JWT 對應伺服器端使用者與員工資料，不接受 body、query 或 path 中的 actor ID 作為授權身分。
2. 將「能呼叫功能」與「能操作哪一筆物件」分開。每個讀、寫、匯出與附件下載都要做物件層授權。
3. 權限變更、停職或離職後，舊 Token 必須失效；JWT 僅保存穩定識別碼，角色與範圍由伺服器端重新取得或以權限版本驗證。
4. 員工列表採欄位白名單、分頁與明確查詢範圍；薪資、銀行、身分證號及醫療資料使用獨立資源與獨立角色。
5. 主管範圍以有效日期的組織關係計算，不以使用者傳入 `department_id` 或 `employee_id` 決定。
6. 管理員例外操作仍須填寫理由，寫入不可變更稽核事件；避免「admin 可做所有事」成為薪資與個資的通用授權。
7. 所有拒絕回應使用一致格式；除合法查詢者外，不區分「不存在」與「存在但無權」。

## Web 安全補充

- 系統使用 Bearer Token 存於瀏覽器 `localStorage`，傳統 Cookie CSRF 不是主要風險；同源 Stored XSS 反而可直接竊取 Token。
- 上傳只信任宣告 MIME，且保留原副檔名。攻擊者可上傳宣告為圖片的 HTML，再由 `/upload` 同源開啟，造成高影響 XSS。
- 附件下載應改為經授權的 API，回傳 `Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`，並使用伺服器產生的不可預測檔名。
- CORS 公開測試未對惡意 Origin 回傳允許標頭，但正式服務缺少 CSP、HSTS、`nosniff` 等常見安全標頭，並暴露 `X-Powered-By`。
